# Add an item to the cart

## Intent

A developer or script needs to put a new item in the one in-memory cart with `POST /items`. This intent builds the whole write path and everything later intents stand on: the pydantic models, the thread-safe `CartStore` (with `list_all` as the read path that proves what was stored), the error shape and the handler that turns every validation failure into 400 `validation_error` (never 422). Done: the PRD's S1 works by hand with `curl`, a rejected body stores nothing, 100 concurrent adds leave 100 items with 100 distinct ids, and ruff and mypy are clean.

## Non-goals

- Do not add update, delete, totals, currency, persistence, authentication or any endpoint the PRD does not list.
- Do not add `GET /items/{id}` or change `GET /items`: view-item and list-items own them.
- Do not hold or compare a price as a float.
- Do not put validation or id generation in a route function: it lives in `models.py` and `store.py`.
- Do not add a runtime dependency beyond fastapi and uvicorn (pydantic ships with fastapi; httpx is test-only).

## Design

| Part | Responsibility | Must not |
|---|---|---|
| `models.py` `ItemCreate` | strict request model: name, price, quantity; trims name; ignores unknown fields | import `store.py` or `errors.py` |
| `models.py` `Item` | the four-field item (id, name, price, quantity); price leaves as a JSON number | hold price as float |
| `store.py` `CartStore` | in-memory cart: `add`, `list_all`, one `threading.Lock` around id draw plus append | import FastAPI or know HTTP |
| `errors.py` | error body `{"error", "message"}`; `RequestValidationError` handler answering 400 | import `store.py` |
| `main.py` | module-level `store`, `POST /items` (201), registers the handlers | hold business rules |
| `tests/conftest.py` | `client` fixture that swaps a fresh `CartStore` into `cart.main.store` | touch the real store between tests |

## Behaviours

- B1 (FR-1, AC-1.1, DR-1): POST /items with `{"name": "Coffee beans", "price": 8.5, "quantity": 2}` answers 201 with exactly `{"id": "<id>", "name": "Coffee beans", "price": 8.5, "quantity": 2}`; an item has exactly four fields: `id` (string), `name` (string), `price` (number), `quantity` (integer).
- B2 (FR-1, AC-1.1): the added item is stored: `CartStore.list_all()` holds it after the 201.
- B3 (FR-1, AC-1.2): two adds with identical name, price and quantity both answer 201 with different ids, and `list_all()` holds both items.
- B4 (FR-1, DR-2): the id is a UUID version 4 in canonical lowercase hyphenated form, generated by the server, unique within the process and never reused; a client-supplied `id` is never used.
- B5 (FR-1, DR-3): `name` is stored exactly as sent apart from leading and trailing whitespace, which is trimmed (`"  Coffee beans "` is stored as `"Coffee beans"`); the trimmed value is non-empty.
- B6 (FR-1, DR-4): `price` is held as `decimal.Decimal` with at most 2 decimal places and at least 0 (0 is allowed), and is returned in JSON as a number (8.5, not "8.50").
- B7 (FR-1, DR-5): `quantity` is an integer of at least 1 with no upper limit (1000000000000 is accepted).
- B8 (FR-1, AC-1.7): a body field other than name, price and quantity, `id` included, is ignored and the server generates the id itself.
- B9 (NFR-1): 100 concurrent adds in the same process leave exactly 100 items with 100 distinct ids; none is lost and no id is reused.
- B10 (NFR-1): `add` draws the id and appends under one `threading.Lock`, and `list_all` takes the same lock and returns a copy, so a reader never sees a half-added item (proposed at chart).
- B11 (NFR-2): ruff and mypy report 0 errors. [sensor: lint, types]

### Failure behaviour

- B12 (FR-1, AC-1.3): WHEN `name` is missing, not a string (5, null), empty, or only whitespace, POST /items answers 400 `validation_error` and stores nothing.
- B13 (FR-1, AC-1.4): WHEN `price` is missing, not a JSON number (the string "8.50", null and a boolean count as not a number), negative (-0.01), or has more than 2 decimal places (8.505), POST /items answers 400 `validation_error` and stores nothing; NaN and Infinity are rejected the same way (proposed at chart).
- B14 (FR-1, AC-1.5): WHEN `quantity` is missing, not a JSON integer (8.0, "2" and true are rejected), or below 1 (0, -1), POST /items answers 400 `validation_error` and stores nothing.
- B15 (FR-1, AC-1.6): WHEN the body is not valid JSON, is empty, or is not a JSON object ([], "x", 5, null), POST /items answers 400 `validation_error` with a message that names `body`, and stores nothing (proposed at chart for the `body` naming).
- B16 (FR-1, AC-1.8): WHEN a request is rejected the message names the offending field: `{"name": "Tea", "price": 3, "quantity": 0}` answers 400 `{"error": "validation_error", "message": "quantity must be an integer of at least 1"}`; the other messages follow the same "<field> must be ..." form (proposed at chart).
- B17 (FR-1, AC-1.8): WHEN several fields are invalid the message names the first in the order name, price, quantity, in one 400 body (proposed at chart).
- B18 (FR-1, AC-1.3): every validation failure is answered 400 with `{"error": "validation_error", "message": "<text>"}` by an exception handler; FastAPI's default 422 body is never returned.
